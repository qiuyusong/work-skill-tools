# Aile 规格驱动开发

## 概述

以当前项目规则和有效规格为基础，执行“只读分析 → 明确确认 → 测试先行 → 最小实现 → 规格回补”的完整流程。

**核心原则：修改授权必须建立在用户已经看到并确认的方案上；代码、测试和文档必须表达同一套最终有效逻辑。**

## 规则来源

开始任务时按顺序读取：

1. 全局 `AGENTS.md`。
2. 仓库根目录 `AGENTS.md`。
3. 目标文件目录链上更具体的 `AGENTS.md`。
4. `docs/README.md`、相关 `docs/specs`、`docs/modules`、`docs/api`、`docs/database` 和历史计划。
5. 相关实现、测试、配置和近期变更。

从规则中提取本次适用的分层、命名、注释、异常、日志、DTO、Mongo、Saga、Feign、测试和文档要求，作为实施与交付检查清单。不得在 Skill 中用通用偏好替代项目规则。

## 任务分类

| 类型 | 确认前允许的工作 | 进入修改阶段的条件 |
|---|---|---|
| 新功能或行为调整 | 读取、定位、可行性分析、方案设计 | 用户确认方案和范围 |
| 问题排查 | 复现分析、日志与代码定位、原因判断 | 确认需要修改且用户批准修正方案 |
| 执行既有计划 | 审查计划、核对当前代码和规则 | 用户明确要求执行该计划，且计划仍有效 |
| 重构 | 现状分析、方案比较、收益与影响评估 | 用户确认重构方案 |
| 新框架或核心依赖 | 必要性分析、备选方案、迁移与恢复设计 | 单独获得二次确认 |
| 纯文档或配置修改 | 读取现状、给出文件和内容方案 | 用户确认修改范围 |

只读定位不需要修改授权。不要因等待确认而停止收集能够完善方案的只读证据。

## 阶段一：只读分析

1. 检查 Git 状态，识别并保护用户已有修改。
2. 找到当前有效规格、模块说明、接口契约、数据模型和测试。
3. 对比用户期望、规格描述和代码行为；出现不一致时明确列出，不静默选择。
4. 判断影响边界：入口、Service、共享契约、持久层、缓存、消息、Saga、配置和依赖服务。
5. 形成推荐方案；存在实质取舍时提供两到三种方案并解释推荐依据。
6. 将验收口径改写为可测试条目。

输出必须使用以下结构：

```text
需求理解
方案设计
涉及模块与包结构
修改或新增文件
关键改动与测试方案
文档回补范围
风险说明
等待确认
```

确认前禁止修改代码、测试、配置和文档，禁止输出补丁。

## 阶段二：确认闸门

把用户确认绑定到以下内容：

- 当前方案版本。
- 允许修改的模块和文件范围。
- 接口、数据和配置影响。
- 测试与文档范围。

“开始改”“可以修改”“按方案执行”或语义明确的同等表达可以进入实施阶段。

实施中出现以下任一变化时立即暂停并重新确认：

- 增加未展示的模块或公共契约。
- 新增或改变数据字段、索引、迁移方式。
- 引入新框架、SDK、中间件或核心依赖。
- 从局部调整扩大为跨模块重构。
- 改变部署、兼容或交付范围。
- 原方案的核心假设被代码事实推翻。

不要把原功能授权解释为对扩大范围的授权。

## 阶段三：计划落盘

确认后在 `docs/plans/{工作编号或中文主题}/` 维护：

- `analysis.md`：需求理解、现状证据、方案取舍、验收条件和风险。
- `plan.md`：跨模块、多步骤或复杂任务的实施顺序、文件、测试和状态。

小型局部调整可以只维护 `analysis.md`。计划最后一步固定为：

```text
核对最终实现、测试结果和当前规格，并按最新有效逻辑回补相关文档及索引。
```

## 阶段四：测试先行与最小实现

对新功能、行为变化和问题修正执行：

1. 根据已确认验收口径编写最小目标测试或复现场景测试。
2. 运行测试，确认其因目标行为尚未实现而按预期不通过。
3. 完成使测试通过的最小代码。
4. 运行目标测试和受影响模块测试。
5. 仅在测试保持通过时整理重复代码、命名和结构。
6. 补充必要的边界、异常、契约和协作测试。

严格遵守项目 `AGENTS.md` 的开发风格。禁止顺带修改无关代码；发现无关问题时只记录并告知用户。

如果测试无法执行，记录原因、替代检查和未验证范围，不得宣称测试已经通过。

## 问题修正分支

先判断问题性质：

### 代码与有效规格不一致

- 增加能够复现差异的测试。
- 修正最小实现。
- 在 `analysis.md` 记录预期行为、实际行为、复现条件、原因、影响范围、需求错误点和测试映射。
- 规格表述已经准确时，不为制造改动而重复改写规格。

### 规格错误或含糊

- 将其视为需求口径变化。
- 先向用户确认修正后的业务规则和验收条件。
- 确认后修改测试、实现和当前有效规格。

### 数据、配置或运行环境问题

- 没有代码变化时不制造无意义代码测试。
- 提供可复现的验证步骤和处理记录。
- 配置或操作规范变化时更新对应指南和交付说明。

## 重构与新框架二次确认

提出方案时必须包含：

1. 当前设计限制和调整必要性。
2. 两到三种可选方案及优缺点。
3. 推荐方案和选择依据。
4. 模块、接口、数据、配置和部署影响。
5. 兼容、迁移、测试和恢复计划。
6. 需要更新的规格、架构决策和交付文档。

优先判断原确认方案是否仍能正确且可维护地完成需求。可以完成时，继续原范围并把扩大调整列为独立建议；无法合理完成时，暂停当前实施并等待二次确认。

## 中文需求规格

新增需求规格使用有业务含义的中文文件名：

```text
docs/specs/{业务主题}需求规格.md
docs/specs/{业务主题}系统设计规格.md
docs/specs/{业务主题}接口规格.md
```

工单编号、通用缩写和框架名称可以保留，但必须搭配中文主题，例如 `AL-2534-机器人提示词配置需求规格.md`。

禁止新增 `spec.md`、`feature.md`、`new-spec.md` 等无明确业务语义的规格文件。现有英文规格需要重命名时，先把重命名及全部引用更新列入方案，不批量处理无关文档。

需求规格根据复杂度覆盖：

- 文档状态、版本、更新时间和关联工作项。
- 背景、目标、范围和非目标。
- 术语、角色、权限和业务边界。
- 当前行为、目标行为和业务规则。
- 主流程、分支流程、异常和边界场景。
- 接口、数据、缓存、消息和跨服务影响。
- 性能、兼容、日志和可观测性要求。
- 可测试的验收条件和测试映射。
- 发布、迁移、恢复要求和变更记录。

规格描述系统应该具备的行为，不堆叠实现代码。

## 文档回补

验证通过后，以最终有效逻辑更新：

| 内容 | 位置 |
|---|---|
| 业务规则和验收口径 | `docs/specs` |
| 分析、计划和问题错误点 | `docs/plans` |
| 模块职责 | `docs/modules` |
| 接口契约 | `docs/api` |
| 模型、索引和迁移 | `docs/database` |
| 整合、操作和开发指南 | `docs/guides` |
| 重要技术选型 | `docs/decisions` |
| 交付、发布、迁移和恢复 | `docs/delivery`、`docs/release` |

规格文件维护当前有效逻辑。历史原因和方案取舍放入计划、决策或交付文档。新增或重命名文档后更新 `docs/README.md`。

## 完成检查

完成前逐项确认：

- 改动范围与确认方案一致。
- 用户已有修改未被覆盖或混入。
- 项目规则检查清单全部处理。
- 目标测试、模块测试和必要构建有实际结果。
- 代码、测试、规格和验收条件一致。
- 中文规格命名和内容结构符合要求。
- 新框架或扩大重构已获得二次确认。
- 文档索引、计划状态和交付说明已经更新。
- 未验证内容和剩余风险已经明确说明。

未经明确要求，不执行 Git 提交、推送或合并。

## 常见错误

| 错误想法 | 正确处理 |
|---|---|
| “只读定位也要等确认” | 确认前继续收集只读证据，只有写入操作需要授权 |
| “时间紧，方案后直接实现” | 等待明确确认，时间压力不改变授权边界 |
| “原需求批准了，新框架也可以一起做” | 新框架和扩大重构需要二次确认 |
| “补一个 `spec.md` 就够了” | 使用中文业务主题并维护结构化当前规格 |
| “测试以后再补” | 先证明目标测试按预期不通过，再做最小实现 |
| “发现顺手能优化的代码” | 不修改无关代码，只记录为后续建议 |
| “文档追加一段新规则即可” | 修正失效内容，保持当前有效逻辑一致 |

## 示例

用户提出新功能后，先读取相关代码和规格，输出方案并等待确认。确认后创建分析记录，增加目标测试并验证其按预期不通过，再完成最小实现。若过程中发现需要引入新流程框架，暂停扩大范围，提交方案比较和迁移计划；只有获得二次确认后才实施。最终使用中文业务主题更新规格，并同步测试映射、模块文档和交付说明。
